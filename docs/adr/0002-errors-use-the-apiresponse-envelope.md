# Errors use the ApiResponse envelope

Every error the API returns has the body of `ApiResponse.error(code, message)`: `success` is false, `error` is a stable code, and `message` is safe to show to the user. `GlobalExceptionHandler` maps the project's exceptions to codes such as `UNAUTHORIZED`, `FORBIDDEN` and `RATE_LIMITED`; the last also carries `retryAfterSeconds`. Request bodies that fail `@Valid` get `VALIDATION_ERROR` with `field: message`. The handler extends Spring's `ResponseEntityExceptionHandler`, so Spring MVC's own errors keep the status Spring chooses: 400 for a missing parameter, 404 for an unknown path, 405 for a wrong method. Their code is the status name and their message is Spring's reason. Anything else is a 500 `INTERNAL_ERROR` with a generic message, and the exception goes only to the server log.

Spring's ProblemDetail format (RFC 9457) is the default once a handler extends `ResponseEntityExceptionHandler`, and Spring Boot has its own default error JSON. Either would give the app and the admin panel a second error shape to read alongside `ApiResponse`. Passing an unexpected exception's message to the client would expose SQL, hostnames and other internal details.

Clients read `error` to decide what to do and `message` to show the user. A new exception type gets its own handler and code in `GlobalExceptionHandler`, and no message may carry internal details. A request that fails in a servlet filter, before Spring MVC, still gets Spring Boot's default error body. Today the authentication filters can fail that way only if loading the user from the database fails.
