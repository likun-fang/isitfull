# Per-IP rate limits allow for carrier-grade NAT

The public read endpoints are limited per client IP address with `@RateLimit`. `/api/v1/rvms/nearby` and `/api/v1/rvms/{id}` allow 600 requests a minute, `/api/v1/rvms/all` and `/api/v1/rvms/batch` allow 300, and `/api/v1/stats/dashboard` and `/api/v1/users/top-contributors` allow 120. `RateLimitAspect` keeps one Redisson rate limiter in Redis for each endpoint and address. It reads the address from the first entry of `X-Forwarded-For`. Caddy sets that header to the client's own address and ignores any value the client sent, and the backend can be reached only through Caddy, because `deploy/docker-compose.prod.yml` publishes no backend port.

The security review proposed 30 to 120 requests a minute. Three, Vodafone and eir put mobile users behind carrier-grade NAT, so hundreds of app users can share one public IPv4 address. A single map pan also sends several `/nearby` requests per user, so limits that low would block whole mobile networks at busy times. Limiting per user or per device does not work for these endpoints: they need no sign-in, and the client chooses its own device ID. Without limits, anyone could scrape the machine list or flood the API.

`@RateLimit` has only limited anything since pull request #2. Before that, the aspect called Redisson's `setRate` on every request, which also clears the requests counted so far, so no limit ever applied, including the older ones on login, refresh and feedback. A new public endpoint gets a per-IP limit sized for shared addresses. A changed limit takes effect once the endpoint's Redis key has been idle for an hour, or after the key is deleted. If a CDN or another proxy is ever put in front of Caddy, it must be listed in Caddy's `trusted_proxies`; otherwise every request appears to come from that proxy.
